# Підключення PHP-бота до h00k.top

PHP-папка `www` працює на окремому OVH-хостингу. Репозиторій `maks37614/h00k` містить Node.js-сайт для VPS. Бот підключається до **працюючого сайту**, а не читає ціни з GitHub.

Серверний канал реалізований у `server/paperFeed.ts`, його реєстрація — в `server.ts`, читання кешу — в `server/marketService.ts` і `server/marketTickerFeed.ts`, план кількох TF — у `server/formationScanPlan.ts`, існуючий worker — у `server/cronService.ts`. Окремий PHP-клієнт знаходиться в папці `www` цього репозиторію; архів оновлення — `www-v4-audited.zip`. Контракт джерела залишається v2 з `collection` і `formationData` на монетах: час збору, закриття останньої свічки та неперервність. PHP v4 блокує нові входи формацій без цих доказів, тому оновіть обидві частини. Docker виключає PHP-папку з образу; запуск PHP на VPS не потрібний.

## 1. Оновити наявну інсталяцію h00k на VPS

Спочатку об'єднайте PR із цими змінами у `main` репозиторію **maks37614/h00k**. Це окремий репозиторій від `maks37614/hook`.

Підключіться до VPS звичним SSH-способом. Перейдіть у **наявний каталог h00k**, де лежать робочі `compose.yaml` та `.env`. Перевірте джерело і поточну гілку:

```bash
git remote get-url origin
git branch --show-current
git status --short
docker compose ps
```

Очікується джерело `maks37614/h00k`, гілка `main`, Docker-сервіс `app`. Збережіть незакомічені правки перед оновленням. Не створюйте другий клон із другим запущеним застосунком. Якщо зараз працює старий `hook2`, не підмінюйте йому лише адресу Git: у цих інсталяцій різні Docker volumes, і для перенесення потрібно окремо зберегти та підключити його дані.

Для **наявної інсталяції h00k із сервісом app**:

```bash
git pull --ff-only origin main
umask 077
cp .env ".env.before-paper-$(date +%Y%m%d-%H%M%S)"
openssl rand -hex 32
nano .env
```

Остання команда перед редактором показує випадковий 64-символьний токен. Додайте його у `.env` і збережіть цей самий рядок для PHP-кабінету:

```dotenv
HOOK_PAPER_FEED_TOKEN=ВСТАВТЕ_СВІЙ_ВИПАДКОВИЙ_ТОКЕН
HOOK_SCREENER_TIMEFRAMES=1m,5m,15m,1h,4h,1d
```

Не копіюйте буквальний текст-підказку як токен. Якщо `HOOK_PAPER_FEED_TOKEN` уже налаштований і підключений до бота, залиште його значення. **Не перезаписуйте весь `.env` прикладом:** решта приватних налаштувань сайту має зберегтися. Токен каналу, пароль кабінету і cron-ключ — три різні секрети. Токени не додавайте в Git або чат.

`HOOK_SCREENER_TIMEFRAMES` налаштовується один раз. Після цього у PHP-кабінеті можна перемикати `1m`, `5m`, `15m`, `1h`, `4h`, `1d` без редагування VPS чи перезапуску контейнера для кожної зміни.

Один існуючий фоновий сканер ділить **спільний бюджет 75 перевірок пар × TF** за цикл між цими TF: 13, 13, 13, 12, 12, 12 відповідно. На кожному TF вибираються найліквідніші доступні futures-пари Binance/Bybit з обсягом від 100 000 USDT. Це менше монет на TF, ніж у старому однотаймфреймовому режимі. Одна монета на двох біржах рахується як дві пари. Конкретна монета не гарантована.

Пара вже відкритої позиції теж може опинитися поза фоновим набором. Тоді бот зберігає її рівні й позначає нестачу даних; автоматичний контроль виходу потребує відновлення справжньої історії. Сам вибір TF не змінює й не закриває таку позицію.

Залишається один таймер раз на 60 секунд; TF обробляються послідовно, спільний знімок тикерів читається один раз, одночасно обробляється до 25 кандидатів. Нових фонових сканерів або керуючих POST-endpoint немає. Це ліміт штатного фонового циклу, а не всіх звернень сайту: ручні скани, інші існуючі задачі й повторні спроби біржевих API мають свої витрати. Повний ручний скан і далі може перевірити до 75 пар для одного TF, а його готовий кеш може використати бот. Фактичне навантаження вашого VPS не вимірювалося.

Для сумісності, якщо нової змінної немає, використовується попередня `HOOK_SCREENER_TIMEFRAME` (типово `1h`). Тому в наявній `.env` потрібно **додати саме рядок із TIMEFRAMES у множині**. Для швидкого скальпінгу залишайте `1m` у списку. Невідомі значення нового списку показують помилку конфігурації, а не тихо підміняють TF. Ручний вибір монети чи TF у PHP не запускає її збір на VPS.

Перебудуйте та відтворіть контейнер, щоб застосувався код і нові змінні оточення:

```bash
chmod 600 .env
docker compose up -d --build app
docker compose ps
docker compose logs --tail=80 app
curl --fail http://127.0.0.1:3000/api/health
```

Якщо у `.env` змінено `APP_PORT`, у локальному curl використайте цей порт. `docker compose restart` сам по собі не оновлює конфігурацію оточення контейнера. Наявний volume `h00k_app_data` зберігається. Під час цього оновлення не запускайте `down -v`.

## 2. Перевірити канал локально і через HTTPS

У цьому самому каталозі виконайте перевірку. Вона читає токен усередині контейнера й виводить лише статус та кількість записів:

```bash
docker compose exec -T app node --input-type=module - <<'NODE'
const token = process.env.HOOK_PAPER_FEED_TOKEN || '';
if (token.length < 32) throw new Error('HOOK_PAPER_FEED_TOKEN не заданий у контейнері');
const query = '?watch=binance:futures:BTCUSDT,binance:futures:ETHUSDT,binance:futures:SOLUSDT&tfs=1m&formationTf=1m';
for (const base of ['http://127.0.0.1:3000', 'https://h00k.top']) {
  try {
    const response = await fetch(base + '/api/paper/formations' + query, {
      headers: { Authorization: `Bearer ${token}` }, redirect: 'error',
      signal: AbortSignal.timeout(15000),
    });
    const text = await response.text();
    let data = {};
    try { data = JSON.parse(text); } catch {}
    console.log({ base, status: response.status, version: data.version,
      snapshots: data.snapshots?.length, quotes: data.market?.quotes?.length,
      candleSeries: data.market?.series?.length, collection: data.collection, error: data.error });
  } catch (error) {
    console.error({ base, error: error.message });
    process.exitCode = 1;
  }
}
NODE
```

Обидві адреси мають повертати JSON із `version: 2`. HTTP `200` означає наявність хоча б котирувань або кешу формацій; для АвтоСкальпінгу перевіряйте також `candleSeries > 0`. Нуль серій може означати, що саме ці пари ще не збираються. Не відкривайте порт 3000 назовні для PHP: використовуйте наявний HTTPS-проксі h00k.top.

Якщо локально все працює, а зовні повертається HTML, сторінка входу або 401 від проксі, для **точного шляху `/api/paper/formations`** потрібно передавати запит до `app` зі збереженим заголовком `Authorization`. Сам endpoint перевіряє власний Bearer-токен. Залиште захист інших шляхів сайта. Наприклад, для наявного Nginx, який проксіює цей застосунок на localhost:3000, у чинному HTTPS `server` може використовуватися окремий блок:

```nginx
location = /api/paper/formations {
    auth_basic off;
    auth_request off;
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header Authorization $http_authorization;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

Це приклад лише для Nginx і такого upstream; не замінюйте ним увесь наявний конфіг. Перевірте `sudo nginx -t` перед `sudo systemctl reload nginx`. Для Caddy чи іншого проксі потрібне відповідне правило. Якщо nginx не має модуля `auth_request`, приберіть саме директиву `auth_request off` з прикладу. Інші API цієї версії сайту не отримують захист від токена PHP-каналу.

## 3. Підключити PHP-бота на OVH

1. Завантажте вміст папки `www` з архіву на PHP-хостинг. Збережіть наявний `config.local.php`, приватний `data_dir` і файл рахунку `state.php`.
2. У `config.local.php` джерело повинно бути:

   ```php
   'source_url' => 'https://h00k.top/api/paper/formations',
   ```

3. Для вашого PHP-хостингу без SSL залишається `require_https => false`. Це стосується входу в PHP-кабінет. Вихідне з'єднання PHP → h00k.top залишається HTTPS з перевіркою сертифіката. HTTP-доступ до кабінету передає пароль та cookie без шифрування.
4. У кабінеті відкрийте **Формації → Налаштування стратегії та фільтрів → Токен формацій VPS**, вставте значення `HOOK_PAPER_FEED_TOKEN` і збережіть. Значення містить лише токен, без слова `Bearer`.
5. У PHP-боті з підтримкою швидкого вибору відкрийте **Формації → Таймфрейм формацій**, оберіть TF і натисніть **Застосувати таймфрейм**. Вибір у старих повних налаштуваннях також працює. Нові входи використовують його після наступного cron; відкриті позиції, їхній TF, стопи, цілі та історія зберігаються. Показаний фоновий план VPS — це конфігурація зі свіжої відповіді джерела, а не підтвердження готовності кожного сигналу. Якщо TF відсутній у плані або свіжому кеші, бот очікує дані. АвтоСкальпінг має окремі TF, кнопку запуску й параметри.
6. Налаштуйте щохвилинний запуск **cron.php на PHP-хостингу**. Адреса та окремий cron-ключ показані в захищеному кабінеті. Для оновленого PHP-бота, який підтримує OVH-заголовок, використовуйте GET або POST і `X-Hook-Cron-Key: ВАШ_CRON_КЛЮЧ` (тільки ключ, без Bearer). Сумісний спосіб — `Authorization: Bearer ВАШ_CRON_КЛЮЧ`, якщо хостинг передає Authorization у PHP. Ключ у URL не підтримується. За доступності щохвилинного CLI-планувальника можна виконувати `php /повний/шлях/www/cron.php`. Саме відкриття сторінки бота не замінює cron.

Для першої інсталяції, коли приватного конфігу ще немає, скопіюйте `config.example.php` у `config.local.php`, задайте випадковий `setup_key` від 32 символів і доступний для запису `data_dir` поза публічним каталогом. У браузері завершіть створення пароля. Не створюйте новий рахунок поверх існуючих даних.

## Дані й діагностика

- `404`: серверні зміни не розгорнуті або запит потрапив до іншого застосунку.
- `401`: неправильний токен чи додаткова авторизація проксі. Перевірте локальну й публічну адреси окремо.
- `503` без JSON v2: канал вимкнений через відсутній/занадто короткий токен або відповідь іншого проксі.
- `503` із JSON v2: кеш поки порожній. Після перезапуску дочекайтеся кількох циклів штатного сканера; якщо джерела недоступні, перевірте `sources` у JSON і журнал `app`.
- `200`, але бот очікує свічки: потрібні пари/таймфрейми відсутні в готовому кеші, дані застарілі або для індикаторів бракує історії. Старші TF можуть потребувати тривалого прогріву на PHP-хостингу.

Канал експортує лише обмежений наявний кеш: до 12 вибраних інструментів, 6 TF, 200 свічок на серію; формації — до 4 останніх вибірок потрібного TF. Поле `collection` повідомляє план фонового сканера. Endpoint не викликає біржі, AI чи сканер, а зміна `formationTf` лише обирає готовий знімок. Залишається невелике навантаження на читання, JSON та мережу. Фактичне навантаження конкретного VPS не вимірювалося. Усі торгові розрахунки бота й віртуальний журнал залишаються на PHP-хостингу; патерни й далі обчислює штатний сканер сайту.

Не додавайте додаткові cron-скани для «прогріву» цього endpoint: він навмисно не добуває відсутніх даних. Монети поза поточною вибіркою штатного сканера не гарантовані. Тестові дані в репозиторії використовуються тільки автотестами й не потрапляють до робочого каналу.

## Перевірка віртуального рахунку

Звіт — [www/AUDIT.md](../www/AUDIT.md). Нові дані перевіряються за початковими часовими позначками; незакрита на момент збору свічка не просувається до фінальної через пізніше читання кешу. Розпізнавач більше не підставляє стандартні відсоткові стопи/цілі для некоректної геометрії; хвилинні ID мають `1m`. Старі завершені угоди не перераховуються за відсутньою історією.

PHP v4 перевіряє грошовий журнал, показує застереження щодо хвилини входу/котирувань/прогалин і окремо позначає старі угоди. Win rate виводиться з усіх завершених віртуальних угод після витрат, а не з confidence формацій. Точний порядок угод усередині OHLC та фактичне біржове виконання цією моделлю не доводяться.
