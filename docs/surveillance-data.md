# Дані стеження: DOM, щільності та бектест

## Видалення монети

Кнопка «Видалити» розташована на кожній картці. Панель дій переноситься на новий рядок на вузькому екрані. Поки запит виконується, повторне натискання заблоковане. Невдалий запит показує помилку й дозволяє повторити спробу.

API видаляє монету лише зі списку її власника та зупиняє відповідний воркер. Видалення останньої монети зберігається після оновлення сторінки й перезапуску сервера. Відкрите вікно видаленої монети закривається.

## Що означає DOM

Стакан містить опубліковані біржею сукупні обсяги на цінових рівнях BID/ASK. Один рівень може складатися з багатьох заявок. Публічний потік не доводить, що це одна заявка одного трейдера, і не гарантує виконання: обсяг може змінитися або бути скасований. Прихована ліквідність та виключені біржею типи заявок у цьому потоці відсутні.

Джерела:

- Binance Spot / USDT Futures: REST-знімок із `lastUpdateId`, буфер WebSocket-оновлень і перевірка їхньої послідовності. Для Futures перевіряється зв'язок `pu` з попереднім `u`.
- Bybit Spot / Linear: `orderbook.1000.SYMBOL`, спочатку `snapshot`, потім `delta`. Новий знімок повністю замінює книгу. Нульова кількість видаляє рівень. Номери `seq` не вважаються обов'язково послідовними через одиницю.

Символ, біржа й ринок не підмінюються іншою монетою або Spot/Futures. Міжнародні символи зберігаються повністю. Неповний Binance-пакет не приймається за повний знімок. Неприпустимі числа, прострочені пакети й перетин BID/ASK вимагають повторної синхронізації.

Застосунок використовує консервативний термін свіжості 5 секунд. Враховується час біржової події, локальне отримання, час HTTP-запиту та зберігання стану в браузері. Застарілі рівні й щільності не показуються як LIVE. Після нового знімка тривалість щільності відраховується заново. Серверу потрібен коректний системний час.

У вікні відображаються найближчі 7 рівнів кожної сторони; детектор перевіряє всі відомі йому рівні, включно з рівнями поза цим коротким списком. Початковий знімок Binance і підписка Bybit мають обмежену глибину. Відсутність щільності означає відсутність у доступних даних, а не в усій прихованій або невідомій частині книги.

Офіційні правила:

- [Синхронізація Binance Futures](https://developers.binance.com/en/docs/products/derivatives-trading-usds-futures/websocket-market-streams/How-to-manage-a-local-order-book-correctly)
- [Стакан Bybit: snapshot, delta та поля відповіді](https://bybit-exchange.github.io/docs/v5/websocket/public/orderbook)

## Пошук за сумою

Для USDT-пар сума рівня в USDT дорівнює `ціна × кількість`.

| Режим | Який поріг застосовується |
| --- | --- |
| MANUAL | Вказана користувачем сума; рівень проходить, якщо його сума не менша за поріг. |
| AUTO | Адаптивний поріг за обсягом торгів і типовими сумами рівнів стакана. |
| HYBRID | Більший із ручного та адаптивного порогів. |

Сусідні рівні не підсумовуються для досягнення порогу. Наприклад, два рівні по 600 USDT не утворюють щільність 1000 USDT. Якщо потрібного рівня немає, активний воркер чекає наступних оновлень реального DOM. Пауза, відключення чи несинхронізована книга припиняють показ актуальних щільностей.

Зменшення суми нижче порогу або кількість `0` прибирає рівень зі списку. Якщо рівень зник і повернувся до обробки черги подій, черга віддає один поточний обсяг, без повторення старої суми. Налаштування Telegram та категорії сповіщень керують доставкою окремо від самого пошуку.

## Щільності на HookChart

У панелі «Поріг щільностей» над будь-яким HookChart поле «Дистанція від ціни» задає максимальну відстань рівня від середини поточного bid/ask у відсотках: від 0,1% до 20%, типово 5%. Межі включені з обох боків. Поле використовує ту саму збережену в профілі настройку, що й повні налаштування графіка. Зміни дистанції та порогу застосовуються одразу, без очікування наступного біржового оновлення.

HookChart перевіряє весь отриманий стакан і показує всі рівні, які одночасно проходять поріг суми, дистанцію та час утримання. Ліміт 40 рядків у внутрішньому короткому списку не обмежує пошук щільностей. Це окремі біржові цінові рівні з сумою `ціна × кількість`; сусідні заявки не об'єднуються. Заявка з кількістю 0 або сумою нижче порогу зникає одразу. Історичні реакції на вже зняті заявки не видаються за поточні щільності.

AUTO у HookChart рахується окремо для поточної біржі, ринку й монети за USDT-сумами рівнів у вибраній дистанції. Ціна монети сама по собі не задає поріг. Найбільші 10% сум (щонайменше одна заявка) виключаються з оцінки звичайного обсягу. Для решти береться більший із `медіана × 3` та `Q75 + 3 × (Q75 − Q25)`, застосовується користувацький множник, потім сума округлюється вгору до цілого USDT, мінімум 1 USDT. Завдяки цьому велика заявка не визначає власний поріг, а рівномірний стакан може не мати жодної щільності. Поріг перераховується раз на 5 секунд, після нового знімка та зміни дистанції або множника — одразу.

Без двох придатних рівнів AUTO показує очікування даних, а не фіктивні $50 000 чи ручну суму іншої монети. Поточний автоматичний поріг показується і в швидкій панелі, і в повних налаштуваннях. Простий фокус у полі суми зберігає AUTO; редагування суми вмикає MANUAL. При переході до MANUAL копіюється поточна сума без округлення до тисячі. Ручний поріг залишається явно заданою користувачем сумою.

Binance використовує спільний перевірений синхронізатор REST-знімка та WebSocket-оновлень: перше оновлення має перекривати ID знімка, наступні мають бути без пропусків. Bybit починає зі snapshot і замінює книгу при новому snapshot або перезапуску `u=1`. Неправильний, перехрещений, застарілий чи відключений стакан очищається; підключення відновлюється автоматично. Статус у панелі показує «Стакан наживо» лише для актуальних даних. Після повторного знімка час утримання починається заново.

Живий стакан HookChart надходить через WebSocket самого сайту `/api/hookchart/depth?exchange=binance&market=futures&symbol=BTCUSDT`. Біржове підключення та завантаження знімка виконує Node.js-сервер. Браузеру не потрібні прямі з'єднання з REST/WebSocket Binance або Bybit для пошуку щільностей. Одна біржа/ринок/монета має спільне підключення для всіх відкритих графіків; новий графік спочатку отримує повний актуальний знімок, потім дельти. Після закриття останнього графіка ресурс звільняється. Канал містить лише публічні рівні біржі, без особистих даних стеження.

Панель розрізняє підключення, синхронізацію, відновлення та недоступний стакан; у Replay живий стакан явно вимкнено. Час біржової події перевіряється на сервері, а до годинника браузера переводиться за першим службовим повідомленням із консервативним урахуванням часу відкриття з'єднання. Таким чином різниця годинників не залишає всі заявки в очікуванні, а старі й затримані повідомлення не стають свіжими. Браузер і сервер прибирають щільності при втраті актуальності даних.

Дистанція обмежує відображення в доступній біржовій глибині, а не розширює її: початковий Binance-знімок містить до 1000 рівнів на сторону, Bybit — до 1000 для ф'ючерсів і споту. Навіть при 20% щільності за межами отриманої книги невідомі.

## Що обчислює бектест

Це модель **ретесту підтримки на OHLC-свічках**, а не відтворення історичного стакана чи журнал реально виконаних угод. Поточний DOM не використовується як доказ ліквідності в минулому.

- Інтерфейс запитує 200 свічок `15m` саме обраної біржі й ринку. Запит бектесту вимагає нового придатного API-відгуку; старий кеш при збої біржі не підставляється. Відмови 403/451, ліміт 429 та HTML замість JSON завершують запит без перебору дзеркал.
- Використовуються лише коректні закриті свічки, закриті вже на початок запиту. Свічка, яка ще формувалася при запиті, не стає фінальною через час завантаження.
- Розриви історії розділяють її на окремі ділянки. Конфліктні дублікати, неприпустимі OHLC/обсяги й неповний майбутній горизонт не створюють результати.
- Сигнал визначається лише за минулими свічками. Модель LONG має TP `+1.5%`, SL `−0.8%`, горизонт `4h`. Це параметри цієї моделі, а не рівні всіх живих сетапів воркера.
- Якщо в одній свічці торкнуті і TP, і SL, порядок торкань невідомий: консервативно зараховується SL. Комісії та прослизання не моделюються.
- Частка успіху означає TP раніше SL у межах горизонту; TIMEOUT не зараховується як TP. Ріст/падіння та 15m/1h/4h-зміни вимірюються за відповідний часовий горизонт, навіть після раннього TP/SL. Вони не є фактичним P&L угоди.

Результат містить біржу, ринок, символ, кількість прийнятих закритих свічок та фактичний період. При недоступних або недостатніх даних API повертає помилку, а не успішний вигаданий звіт.

## Перевірки

`tests/hookchart-depth-stream.test.ts` перевіряє повний локальний канал від біржових WebSocket-повідомлень через справжній серверний адаптер до клієнтського стакана й щільностей, зокрема видалення заявки, різницю годинників, повторне підключення, розділення ринків і спільне підключення кількох графіків. `tests/hookchart-density.test.ts`, `tests/surveillance-dom.test.ts`, `tests/orderbook-sync.test.ts`, `tests/backtest.test.ts` та HTTP-тести стеження перевіряють поріг, дистанцію, скасування рівня, повторну появу, свіжість, синхронізацію, закриття свічок, розриви історії та зупинку воркера після видалення.

Офлайн-тести використовують явно задані фікстури й блокують зовнішню мережу. Їхні котирування не є ринковими даними й не потрапляють до робочого інтерфейсу. Перевірка коду та фікстур не підтверджує доступність WebSocket із конкретного VPS: мережу та статус LIVE потрібно окремо перевірити на самому сервері.

Для перевірки публічних джерел із VPS після оновлення контейнера:

```bash
docker compose exec app npm run audit:surveillance -- --exchange binance --market futures --symbol BTCUSDT --threshold 1000000 --timeout 30
```

Для Bybit використайте `--exchange bybit`, для Spot — `--market spot`. Команда запускає окреме читання публічних потоків. Вона чекає свіжого знімка та щонайменше одного оновлення, перевіряє ручний поріг і запитує історію для бектесту. Результат `success: true` потребує придатних даних обох джерел. `matchingLevels: 0` означає, що на момент перевірки жоден доступний рівень не досяг суми; це не помилка.
